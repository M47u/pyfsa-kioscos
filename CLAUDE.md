# pyfsa-kioscos — Session Starter

Multi-tenant SaaS for kiosco/almacén businesses ("comercios"): the real stock/sales backend that the leads from the sibling project (`AsistenteClientesKiosko`, the lead scraper + WhatsApp outreach + fake demo) eventually get sold into. That project's `/demo/{lead}` is mock data only — this is where the real product lives.

Laravel 12, own git repo (`c:\xampp\htdocs\pyfsa-kioscos`), separate from `AsistenteClientesKiosko` and from the accidental repo at `c:\xampp\htdocs`. One commit so far: base scaffold + tenancy wiring.

## Architecture decisions (already made — don't relitigate)

- **Multi-tenancy**: `stancl/tenancy` v3.10, **database-per-tenant** (each Comercio gets its own real MySQL database). La app YA NO ejecuta CREATE/DROP DATABASE — ver la decisión "Sin CREATE DATABASE en la app" más abajo.
- **Tenant model**: `App\Models\Comercio` (extends Stancl's `Tenant`, `implements TenantWithDatabase`, `use HasDatabase`) — named `Comercio` instead of `Tenant` because that's what it is in the business domain.
- **Tenant resolution: by authenticated user, NOT by subdomain.** Custom `App\Http\Middleware\InitializeTenancyByAuthenticatedUser` replaces the package's default `InitializeTenancyByDomain` in `routes/tenant.php`. It reads `$user->comercio_id` and calls `tenancy()->initialize()`.
  - **Why**: avoids configuring DNS/hosting per new comercio — no subdomain needed to onboard a client.
  - Central `users` table has a `comercio_id` column (string, FK → `tenants.id`, nullable, `nullOnDelete`) — string not `foreignId` because tenant ids are UUIDs.
- **Central DB** (auth + subscriptions + tenant registry): `pyfsa_kioscos_central`.
- **Zona horaria — por comercio, no global**: los comercios pueden estar tanto en Formosa (Argentina) como en Alberdi (Paraguay) — ver sección 04 del documento de alcance —, y a diferencia de Argentina, Paraguay sí tiene horario de verano (UTC-3 en verano, UTC-4 el resto del año), así que un `config('app.timezone')` fijo para toda la app no alcanza. Cada `Comercio` elige la suya (`Comercio::ZONAS_HORARIAS`, solo Argentina/Paraguay, no las ~600 de IANA) **una sola vez, al primer uso**: `EnsureComercioTimezoneIsConfigured` redirige a `/zona-horaria` (`ZonaHorariaController`) mientras el comercio no la eligió, y `InitializeTenancyByAuthenticatedUser::aplicarZonaHoraria()` aplica `date_default_timezone_set()` en cada request según el comercio ya autenticado (con el default de `config/app.php` mientras tanto). El atributo `timezone` no tiene columna propia en `tenants`: stancl/tenancy guarda cualquier atributo no-columna dentro del JSON `data`, no hizo falta migración. **Gotcha menor, no bloqueante**: la sesión de MySQL usa `time_zone = SYSTEM`, que en esta máquina resuelve al huso del SO (Argentina, fijo, sin DST) — el round-trip INSERT/SELECT de una misma fila sigue siendo consistente (misma sesión en ambos sentidos, se ve bien en pantalla para CUALQUIER comercio), pero un cálculo de intervalo entre dos filas de un comercio paraguayo escritas a los dos lados de un cambio de horario de verano puede quedar corrido en una hora. No importa para nada de lo implementado hoy (fechas mostradas tal cual, sin restas de intervalos); revisar si algún reporte futuro hace ese tipo de cuenta. **Gotcha de PHP**: `date_default_timezone_set()` es estado global del proceso — seguro en el modelo actual (una request = un proceso/hilo fresco), se rompería con Laravel Octane (workers persistentes) sin resetearlo al final de cada request.
- **Gotcha de middleware — leer antes de agregar rutas con binding implícito**: `bootstrap/app.php` fuerza `InitializeTenancyByAuthenticatedUser` a correr antes que `SubstituteBindings` vía `$middleware->prependToPriorityList()`. Sin eso, el orden default de Laravel deja `SubstituteBindings` (parte del grupo `web`) corriendo ANTES que nuestro middleware de tenancy, así que cualquier ruta con binding implícito de Eloquent (`Producto $producto`, etc.) intenta resolver el modelo contra la base CENTRAL antes de que la tenancy esté inicializada → 500 en producción, con los tests en verde (`TenantTestCase::setUp()` inicializa tenancy a mano y enmascara el bug). Si agregás una ruta nueva con binding implícito dentro del grupo de `routes/tenant.php`, este fix ya la cubre — pero si tocás `bootstrap/app.php` o el orden de middlewares, revisá esto primero. **No aplica a `Comercio`**: usa `CentralConnection` (ver stancl/tenancy), fuerza siempre la conexión central sin importar el orden de middlewares — por eso el binding implícito de `{comercio}` en `/admin/comercios/{comercio}` no necesita este fix ni tiene su propio test de regresión.
- **Sin CREATE DATABASE en la app (decisión, no relitigar)**: el plan de hosting compartido con el que se va a desplegar esto (documento de alcance, sección 04) no le da al usuario de MySQL de la app el permiso `CREATE DATABASE` — las bases se crean desde el panel del hosting, a mano. La arquitectura database-per-tenant NO cambia, solo cambia QUIÉN crea la base física: antes lo hacía `Jobs\CreateDatabase` (stancl/tenancy) automáticamente al guardar un `Comercio`; ahora la base tiene que existir DE ANTES.
  - `TenancyServiceProvider`: se sacó `Jobs\CreateDatabase` del pipeline de `Events\TenantCreated` (queda solo `Jobs\MigrateDatabase`, que no depende de que `CreateDatabase` haya corrido — verificado en `vendor/stancl/tenancy/src/Jobs/MigrateDatabase.php`, es literalmente `Artisan::call('tenants:migrate', ...)`) y se vació el pipeline de `Events\TenantDeleted` (se sacó `Jobs\DeleteDatabase` — borrar un `Comercio` ya NO borra su base de datos, ver más abajo).
  - `Comercio::asignarBaseDeDatos(string $nombreBase)` asigna el nombre de una base YA EXISTENTE, vía `setInternal('db_name', ...)` (API pública de stancl/tenancy, `Stancl\Tenancy\Database\Concerns\HasInternalKeys` — verificado en `DatabaseConfig::getName()`, que devuelve ese valor si está seteado y solo genera un nombre nuevo si no). Se llama ANTES de `$comercio->save()`. NO hace falta agregar `tenancy_db_name` a `Comercio::getCustomColumns()` — a diferencia de `estado_suscripcion`/`trial_termina_el`, no es una columna real de `tenants`, así que `VirtualColumn` la guarda en el JSON `data` igual que `nombre`/`timezone`.
  - **Alta de un comercio nuevo (procedimiento manual, en orden)**:
    1. PyFsa crea la base de datos vacía en el panel del hosting (cPanel/similar) — el nombre real suele venir prefijado con el identificador de la cuenta (ej. `cpanelUser_kiosco1`), no lo elige la app.
    2. PyFsa entra a `/admin/comercios/create` (`Admin\ComercioController`, dueño-only vía `EnsureUserIsAdmin`) y completa el formulario: nombre del comercio, el nombre EXACTO de la base recién creada, y los datos del primer dueño (nombre/email/contraseña).
    3. Al enviar, `Admin\ComercioCreateRequest::withValidator()` verifica que esa base exista y sea accesible (configura una conexión al vuelo y corre un `select 1`) ANTES de crear nada — un typo en el nombre de la base es un error de formulario, no un comercio a medio crear. Si pasa, `ComercioController::store()` crea el `Comercio` (dispara las migraciones de tenant automáticamente contra esa base) y recién después el `User` dueño.
  - **Borrar un comercio ya NO borra su base de datos**: `Comercio::delete()` sigue borrando la fila central (dispara `Events\TenantDeleted`, pero ese pipeline ahora está vacío) — la base de datos física queda intacta y hay que borrarla a mano en el panel del hosting si corresponde.
  - **`is_admin` no es `$fillable` en `User`** (descubierto de paso al implementar esto, **ya resuelto** — ver "Provisionar admins, auditoría y rate limiting" abajo): `User::where(...)->update(['is_admin' => true])` era un no-op silencioso porque `update()`/`create()` respetan `$fillable`. La decisión fue **dejarlo fuera de `$fillable` a propósito** y setearlo por asignación directa desde un comando artisan (`admin:crear`).
- **Admin/Suscripciones (módulo 3.6 del documento de alcance)**: PyFsa (no el kiosquero) administra manualmente qué comercios tienen acceso pagado — "sin cobro automático en v1". Dos piezas separadas:
  - **Gate del lado del comercio**: `Comercio::tieneAccesoActivo()` (true para `prueba`/`activa`, false para `vencida`/`cancelada`) + `App\Http\Middleware\EnsureComercioSuscripcionActiva` en el grupo de `routes/tenant.php` (después de `InitializeTenancyByAuthenticatedUser`, sin dependencia de orden con `EnsureComercioTimezoneIsConfigured`). Si no tiene acceso activo, redirige a `suscripcion-vencida` (mismo patrón anti-loop que `EnsureComercioTimezoneIsConfigured`: no redirige si la ruta actual ya es esa).
  - **Panel admin** (`/admin/comercios`, `Admin\ComercioController`): CENTRAL, no tenant-scoped — no pasa por `routes/tenant.php` ni por `InitializeTenancyByAuthenticatedUser`, va directo en `routes/web.php` protegido por `auth` + `App\Http\Middleware\EnsureUserIsAdmin` (chequea `$user->is_admin`, columna nueva en `users` central). Listado con estado + fecha de fin de prueba + cantidad de usuarios (`User::where('comercio_id', ...)->count()`, sin relación Eloquent nueva) y un form inline por fila para cambiar el estado.
  - **GOTCHA importante de stancl/tenancy — por qué `estado_suscripcion`/`trial_termina_el` necesitan `Comercio::getCustomColumns()`**: por default, `Stancl\VirtualColumn\VirtualColumn` (con la que `HasDataColumn` es un alias) saca de `$attributes` CUALQUIER atributo que no esté en `getCustomColumns()` (default: solo `id`) y lo empuja al JSON `data` al guardar — sin importar que la columna exista de verdad en la tabla. Sin declarar las columnas nuevas ahí, quedarían siempre `NULL` en su columna real (todo el valor viajaría escondido en `data`), rompiendo cualquier query SQL directa de filtro/listado en el panel admin. `Comercio::getCustomColumns()` ahora devuelve `['id', 'estado_suscripcion', 'trial_termina_el']` — **si agregás OTRA columna real a `tenants` en el futuro, hay que sumarla ahí también, o va a fallar en silencio** (sin error, solo el dato no persiste donde se espera).
  - **GOTCHA de testing derivado del anterior**: `Comercio::create()` no relee la fila después del INSERT, así que el default `'prueba'` de la migración (aplicado en la base) no queda reflejado en el objeto en memoria. Como `Tenancy::initialize()` no reemplaza `tenancy()->tenant` si ya está inicializado con la misma key (ver `vendor/stancl/tenancy/src/Tenancy.php`), el objeto creado en `TenantTestCase::setUp()` queda instalado tal cual durante TODO el test — sin setearlo a mano ahí, `estado_suscripcion` se queda en `null` y `tieneAccesoActivo()` daría `false`, mandando CUALQUIER test que pegue contra el panel a `/suscripcion-vencida`. `TenantTestCase::setUp()` ya lo setea explícitamente (mismo motivo por el que ya seteaba `timezone`).
  - **No hay pantalla para crear admins** (caso de uso interno, es provisioning, no una feature del producto) — se hace con un comando artisan, ver "Provisionar admins, auditoría y rate limiting" justo abajo:
    ```
    php artisan admin:crear tu@email.com --nombre="Tu Nombre"
    ```
- **Provisionar admins, auditoría y rate limiting (gaps de seguridad/proceso encontrados por el usuario, no están en el documento de alcance)**: tres huecos del panel admin, todos alrededor de lo mismo — una cuenta admin toca TODOS los comercios y hasta acá no había ni forma segura de crear una, ni rastro de lo que hacía, ni fricción contra fuerza bruta en la puerta de entrada.
  - **`php artisan admin:crear {email} {--nombre=} {--password=}`** (`App\Console\Commands\CrearAdminCommand`): reemplaza al snippet de tinker que estaba documentado antes y que nunca funcionó (ver el bullet de `is_admin`/`$fillable` arriba). Si el email ya existe como `User` lo promueve; si no, lo crea. **Decisión de diseño, no relitigar: `is_admin` NO se agrega a `User::$fillable`** — es un flag de plataforma, y dejarlo fuera de mass-assignment evita que un `User::create($request->all())` futuro lo abra sin querer. El comando lo setea con asignación directa de propiedad (`$user->is_admin = true; $user->save();`), que es el único camino que se saltea `$fillable` sin desactivarlo para nadie más.
    - **Contraseña, tres caminos en orden de preferencia** (criterio elegido acá, la consigna lo dejaba abierto): (1) `--password=` explícita, con un aviso de que queda en el historial de la shell; (2) terminal interactiva — **el default** —, se pide con `$this->secret()` y se confirma, así no queda ni en el historial (a diferencia de `--password`) ni en el scrollback (a diferencia de una generada e impresa); (3) sin terminal interactiva (`--no-interaction`, un script, CI), se genera una random con `Str::password(20)` y se imprime UNA vez, porque no hay a quién preguntarle y fallar ahí dejaría el provisioning a medias sin alternativa. Nunca se guarda texto plano: el cast `'password' => 'hashed'` de `User` la pasa por `Hash::make` al guardar, mismo mecanismo que `UsuarioController`.
    - **Un admin de plataforma PUEDE además ser dueño de un comercio**: si el usuario que se promueve tiene `comercio_id` no nulo, el comando **avisa pero no bloquea** — es un caso legítimo (probar el producto con datos reales sin una segunda cuenta). El aviso vale la pena igual: esa cuenta pasa a ver su comercio Y el panel de todos.
    - **Valida email y fuerza de contraseña, igual que el camino web** (ronda de hardening posterior): antes aceptaba cualquier string en los dos campos mientras `Admin\ComercioCreateRequest` (alta de un dueño común) sí exigía `email` válido + `Password::defaults()` — la asimetría estaba al revés de donde tenía que estar, porque acá se crea la cuenta MÁS privilegiada del sistema. El email se valida al principio de `handle()`, antes de tocar la base; la contraseña se valida **donde se resuelve** (`resolverPassword()`), no al principio, por dos motivos: así cubre también el camino INTERACTIVO (que es el default, sin `--password` — validar solo la opción explícita dejaba abierto el camino más usado) y no aborta una promoción por una `--password` que en ese camino se ignora igual. La generada al azar (`Str::password(20)`, camino sin terminal) no se valida: por construcción es más fuerte que cualquier default razonable. Las reglas salen de `Password::defaults()`, no de una copia, para que endurecerlas un día alcance a los dos caminos de una sola vez.
    - **Gotcha resuelto — `users` usa `SoftDeletes`**: la búsqueda es con `withTrashed()`. Una fila dada de baja sigue ocupando el email en el `UNIQUE` de la columna, así que sin esto promover a alguien eliminado terminaría en un `SQLSTATE[23000]` ilegible en vez de un mensaje útil. El comando la restaura y la promueve, avisando.
    - Idempotente: si el usuario ya era admin, informa y devuelve éxito sin tocar nada. El email se normaliza a minúsculas antes de buscar/crear.
  - **Auditoría de acciones admin** — tabla CENTRAL `registros_auditoria` (`database/migrations/2026_09_14_100000_*`, **no** `database/migrations/tenant/`: son acciones transversales a todos los comercios, ejecutadas por alguien que no pertenece a ningún tenant) + modelo `App\Models\RegistroAuditoria`.
    - **Sin foreign keys en `user_id`/`comercio_id` a propósito**, mismo criterio ya establecido para las columnas "quién" de un historial (`anulada_por`/`anulado_por`/`user_id` en las tablas de tenant): un log tiene que sobrevivir a que borren al usuario o al comercio que menciona — un `cascade` lo borraría y un `nullOnDelete` lo vaciaría, y en los dos casos dejaría de ser auditoría. Consecuencia directa: el "quién"/"sobre qué" se resuelven **en PHP** en `Admin\AuditoriaController::index()` (no se puede `with()`/join), con dos queries fijas por página — `User::withTrashed()->whereIn(...)` (el admin puede haber sido dado de baja después) y `Comercio::all()` (el `nombre` vive en el JSON `data`, no es filtrable por SQL — ver el gotcha de `VirtualColumn` arriba).
    - `RegistroAuditoria` es **solo-append**: `public const UPDATED_AT = null` (la migración ni crea la columna) y `use CentralConnection` — hoy todas las rutas que escriben acá son centrales, pero si mañana se auditara algo desde `routes/tenant.php` la conexión default ya sería la del tenant, que no tiene esta tabla. Mismo razonamiento que en `User`.
    - `RegistroAuditoria::registrar($accion, $comercioId, $detalles)` es el punto de entrada único desde los controllers y comandos: resuelve solo el `auth()->id()` y el origen (`ip`/`user_agent`) para que ningún call site se olvide del "quién" ni del "de dónde". Acciones: `ACCION_COMERCIO_CREADO` (`'comercio.creado'`), `ACCION_COMERCIO_ESTADO_ACTUALIZADO` (`'comercio.estado_actualizado'`), `ACCION_ADMIN_CREADO` (`'admin.creado'`) y `ACCION_ADMIN_PROMOVIDO` (`'admin.promovido'`), formato `recurso.evento` para que crezcan sin colisionar. Las etiquetas legibles viven aparte en `RegistroAuditoria::ETIQUETAS` — cambiar el texto de la pantalla no debe reescribir el historial ya persistido.
    - Los call sites sobre comercios están en `Admin\ComercioController`: en `update()` el estado anterior se lee **ANTES** del `update()` (después no hay forma de saber de dónde venía, y "de vencida a activa" es justamente el dato que hace útil al registro); en `store()` el registro se escribe **DESPUÉS** del `User::create()` del dueño, porque si esa línea falla el alta quedó a medias (ver el docblock de `store()`) y no corresponde registrarla como un comercio creado.
    - **`update()` audita los DOS campos que persiste, no solo el estado** (hallazgo de la revisión de seguridad, arreglado): `ComercioEstadoRequest` valida `estado_suscripcion` Y `trial_termina_el`, pero la primera versión guardaba solo el estado — extender un trial sin cambiar el estado ("te doy dos semanas más", acción real y frecuente) dejaba una fila que decía "de prueba a prueba", o sea que no cambió nada cuando sí cambió. `detalles` ahora lleva `estado_anterior`/`estado_nuevo` + `trial_termina_el_anterior`/`trial_termina_el_nuevo`, los dos "anterior" leídos antes del `update()`. La fecha se guarda plana con el helper privado `ComercioController::fechaLegible()` porque el cast `'date'` la devuelve como Carbon, que dentro del JSON se serializaría como un objeto entero con timezone y demás ruido. **Regla general derivada: si un formulario admin persiste N campos, los N tienen que estar en `detalles` — un log que afirma que no cambió nada cuando sí cambió es peor que no auditar.**
    - **`admin:crear` también audita** (era la acción MÁS privilegiada del sistema y la única sin rastro): `admin.creado` al crear, `admin.promovido` al promover, con `email`/`usuario_id` y, en la promoción, `restaurado_de_baja` y `ya_era_admin`. `user_id`/`comercio_id`/`ip`/`user_agent` quedan **null** — no hay sesión ni request HTTP en consola, es esperado (ver el gotcha de `SetRequestForConsole` abajo). El caso idempotente puro (ya era admin y la fila no estaba dada de baja) **no** deja registro: no es un cambio, y ensuciaría el log. El caso "ya era admin PERO venía dado de baja" **sí** lo deja: restaurarle el acceso a todos los comercios a una cuenta desactivada es justo lo que un log de seguridad tiene que mostrar.
    - **`ip` (45) + `user_agent` (512) en `registros_auditoria`** (`database/migrations/2026_09_14_110000_*`, migración aparte — la original ya estaba corrida): para investigar una cuenta admin comprometida, DE DÓNDE vino la acción importa tanto como quién la hizo. Las filas viejas quedan en NULL (no hay forma de reconstruirlo hacia atrás). 512 y no el 255 default porque los user-agents de móviles lo pasan cómodos, y `Str::limit(..., 511)` en `registrar()` para que un header gigante falsificado no tire abajo la escritura del registro entero por un dato accesorio. Columna "Origen" en `/admin/auditoria` (IP en mono + user-agent truncado con el completo en el `title`).
    - **GOTCHA importante — por qué `registrar()` NO puede confiar en `request()` a secas ni en `runningInConsole()`** (los dos verificados contra el framework, no supuestos): (1) el kernel de consola bootea `SetRequestForConsole` (`vendor/laravel/framework/.../Bootstrap/SetRequestForConsole.php`), que arma una Request **falsa** con `Request::create(config('app.url'))` — y Symfony rellena ahí `REMOTE_ADDR = 127.0.0.1` y `HTTP_USER_AGENT = 'Symfony'` por default (`vendor/symfony/http-foundation/Request.php`), así que sin guard cada `php artisan admin:crear` en PRODUCCIÓN dejaría un registro afirmando que la acción vino de 127.0.0.1 con un navegador llamado "Symfony": un log que miente, peor que uno vacío. (2) `app()->runningInConsole()` no sirve como guard porque mira `\PHP_SAPI`: bajo PHPUnit devuelve **true siempre**, también en los tests que sí pegan por HTTP — gatear con eso apagaría la captura justo donde hay que probarla y el bug volvería sin que ningún test se entere. Lo que sí distingue los dos casos es **si hay una ruta resuelta** (`request()->route() !== null`): la request falsa de consola nunca pasa por el router, y toda acción admin auditada llega desde un controller. Si algún día se audita algo desde una `Command` que igual quiere dejar origen, el dato tiene que venir por parámetro, no de `request()`.
    - **Si se agrega una acción admin nueva en el futuro, hay que sumarle su `RegistroAuditoria::registrar()` a mano** — no hay un observer ni un middleware que lo haga solo (a propósito: un observer auditaría también los cambios que NO vienen de una acción admin, ensuciando el log).
    - Vista `/admin/auditoria` (`Admin\AuditoriaController`, solo lectura, sin filtros todavía), paginada de a 50, ordenada por `latest('id')` y **no** por `created_at` (dos acciones dentro del mismo segundo empatarían y el orden quedaría librado a MySQL; el id autoincremental sí es monótono). Sumada a `layouts/nav-admin.blade.php`.
  - **Rate limiting en `/login` — DOS límites que se suman, a propósito**:
    1. **Por email + IP** (`LoginRequest::authenticate()`, patrón Breeze que ya venía del scaffolding — `RateLimiter::hit()` en cada intento fallido, `RateLimiter::clear()` en éxito, clave `Str::transliterate(Str::lower(email)).'|'.ip`), pero **no tenía un solo test**. Se cubrió con cuatro casos (ver Testing) y se extrajo el `5` mágico a `LoginRequest::INTENTOS_PERMITIDOS` con el porqué del límite. Frena la fuerza bruta contra UNA cuenta.
    2. **Por IP sola** (`RateLimiter::for('login-por-ip', ...)` en `AppServiceProvider::boot()` + `->middleware('throttle:login-por-ip')` en la ruta `POST /login` de `routes/web.php`), agregado por la revisión de seguridad: el límite 1 NO veía el **credential stuffing** — cada email arranca su propio contador, así que un atacante desde una sola IP podía probar una contraseña contra miles de emails distintos sin encontrar nunca un freno. **20 requests por minuto** (`AppServiceProvider::INTENTOS_LOGIN_POR_IP`): cuatro veces el límite por email, así que cuatro personas distintas detrás del mismo NAT/IP compartida —un comercio con varios empleados, un pueblo con IP compartida del ISP: el caso real de Formosa/Alberdi— pueden agotar cada una su propio margen de tipeo sin pisarse; y 20 emails por minuto es inútil para recorrer una lista filtrada de credenciales. Limiter **con nombre** y no `throttle:20,1` pelado para tener el porqué del número junto a la constante y poder ajustarlo/loguearlo sin tocar las rutas. Ojo con la diferencia de semántica: el middleware `throttle` cuenta TODAS las requests (también las exitosas), a diferencia del `RateLimiter::hit()` manual del límite 1, que solo suma en el fallo — es lo que se quiere acá, un bombardeo que acierta también tiene que frenarse.
    - **Límite conocido, asumido**: el límite 1 incluye la IP en la clave, así que un atacante distribuido (muchas IPs contra el mismo email) sigue teniendo más margen; el límite 2 tampoco lo cubre, por definición. Es el mismo trade-off que hace Laravel de fábrica — sin la IP, cualquiera podría bloquear la cuenta de un comercio ajeno a voluntad con seis intentos basura. Mitigarlo de verdad sería captcha/2FA, otra ronda.
  - **Un admin sin comercio ya no cae en un 403 al loguearse** (bug real encontrado por la revisión de seguridad): `/panel` vive en `routes/tenant.php`, detrás de `InitializeTenancyByAuthenticatedUser`, que hace `abort_if(blank($user->comercio_id), 403)`. Un admin provisionado con `admin:crear` NO tiene comercio (es el caso normal), así que se logueaba bien y se estrellaba ahí, sin llegar a ningún lado usable. **`User::rutaDeInicio()`** concentra la decisión ("admin Y sin comercio → `admin.comercios.index`, si no → `panel`") y la usan los DOS caminos que la tomaban por separado: `AuthenticatedSessionController::store()` (`redirect()->intended(...)`) y el `RedirectIfAuthenticated::redirectUsing()` de `AppServiceProvider::boot()` (el rebote del middleware `guest` a alguien ya logueado que entra a `/login`). ## Verified working

- ~~Creating a `Comercio` auto-creates a real MySQL database; deleting it auto-drops that database~~ — **no longer true, see "Sin CREATE DATABASE en la app" in Architecture decisions**: the database now has to exist beforehand (created by hand in the hosting panel), `Comercio::asignarBaseDeDatos()` just points the tenant at it, and deleting a `Comercio` no longer touches the database at all. Verified via the admin creation flow (`Admin\ComercioTest`) and the test suite's own self-provisioning (see Testing below).
- Auth scaffolding present: `AuthenticatedSessionController` (login/logout), `/login` + `/logout` routes.
- `/panel` is a real dashboard now (`PanelController`): welcome message with the comercio id + shortcut cards to Productos/Clientes/Ventas/Reportes.
- **Shared layout + persistent nav**: `resources/views/layouts/app.blade.php` (classic `@extends`/`@yield` — chosen over anonymous-component slots because every existing view already used plain Blade `@include` for partials, e.g. `productos._form`, so `@extends` kept the same idiom instead of mixing two layout mechanisms) holds the `<!DOCTYPE>`/`<head>`/`@vite` boilerplate and two `@yield` hooks (`body-class`, `container-class`) so each view can still control its own body alignment (centered form vs. top-aligned list) and max-width without repeating markup. `resources/views/layouts/nav.blade.php` is included only inside `@auth` (so `/login` never renders it, no separate flag needed) and highlights the active section with `request()->routeIs(...)`. The two duplicated banners became anonymous Blade components: `<x-status-banner />` (`session('status')`, green) and `<x-validation-errors />` (`$errors->any()`, red) — anonymous components chosen over `@include` for these specifically because they take no parameters and read straight from the view's implicit state, so a self-closing tag reads cleaner than `@include('components.foo')`. All 8 pre-existing views + `auth/login.blade.php` were migrated to extend the layout; no visual/markup change to the page content itself, only how it's wrapped.
- **Stock**: `Producto` (alta con nombre/código de barras/precio costo/precio venta/stock mínimo), stock calculado por `MovimientoStock` (nunca editable directamente), `bajoMinimo()`, búsqueda por nombre o código de barras. Reposición de stock vía `ProductoController::reponerStock`.
- **Ventas + Cliente (mínimo)**: `VentaController` registra una venta con carrito de ítems (online, síncrono — nada de offline todavía), medios de pago efectivo/transferencia/fiado, dentro de una transacción: crea la `Venta`, cada `ItemVenta` con snapshot de `precio_unitario`, y un `MovimientoStock` tipo `venta` con cantidad negativa por ítem. La venta SE BLOQUEA si dejaría el stock de algún producto negativo, en dos capas: `VentaRequest::withValidator` es un pre-check de UX (SELECT simple, sin lock, falla rápido con buen mensaje) y `VentaController::store` es la garantía real contra condiciones de carrera — DENTRO de la transacción trae los productos con `lockForUpdate()` y recalcula el stock antes de crear nada; si no alcanza, lanza `ValidationException::withMessages(['items' => ...])` (mismo tratamiento que cualquier otro error de validación de la app, sin catch manual). Ambas capas agrupan cantidades por producto sumando filas repetidas del carrito — todo o nada, no se vende parcialmente el carrito. `Cliente` mínimo (nombre/teléfono/límite de crédito) con `saldo()` calculado como sus ventas fiadas menos sus pagos.
- **Fiado (módulo completo)**: `Pago` (cliente_id, monto, user_id sin FK — mismo patrón que `movimientos_stock`/`ventas`) resta del saldo del cliente. `Cliente::saldo() = ventas fiadas - pagos` (puede dar negativo si pagó de más, es información válida, no se clampea). `Cliente::superaLimite(?float $saldo = null): bool` (mismo patrón que `Producto::bajoMinimo()`, solo alerta) acepta un saldo ya calculado opcionalmente para que los call sites que ya lo necesitaron no lo recalculen de cero. A diferencia del stock, el límite de crédito de fiado **NO bloquea** la venta — `VentaController::store` deja un flash `advertencia` (no bloqueante) si el cliente queda por encima de su límite después de una venta fiada. `ClienteController::show` arma en memoria (sin tabla propia) el historial cronológico mezclando `ventas` fiadas + `pagos`, más reciente primero. `PagoRequest` valida `monto` (numeric, min:0.01, max:99999999.99 — tope real de la columna `decimal(10,2)`).
- **Reportes (módulo 3.4, 6 bloques — priorización del usuario, "top productos por valor de stock invertido" queda deliberadamente afuera para una ronda futura)**: `ReporteController::index()` arma las 6 secciones en una sola vista, todas con agregados a nivel de SQL/colección para evitar N+1 — nunca `Cliente::saldo()`/`Producto::stockActual()` dentro de un loop. (1) Ventas de hoy y de la semana actual (lunes a domingo — `Carbon::startOfWeek()`/`endOfWeek()`, default de Carbon es lunes) con el día pico destacado: una sola query trae las ventas de la semana, el resto se agrupa/suma en PHP por día. (2) Producto más vendido de la semana **por CANTIDAD, no por facturación** (decisión explícita): un join+`groupBy` a nivel SQL sobre `items_venta`/`ventas` seguido de un solo `Producto::find()` con el ganador. (3) Cuentas por cobrar (fiado) — no estaba en el documento de alcance original, se agregó porque Fiado es el diferenciador del producto: total combinado vía dos `sum()` agregados, y ranking de top-10 deudores vía `Cliente::withSum()` con dos subagregados (`total_fiado`, `total_pagos`), saldo y flag de "supera límite" calculados en PHP sobre la colección ya traída, ordenados en PHP por saldo descendente. (4) Resumen de stock bajo mínimo: solo el conteo (la vista de Productos ya resalta cada fila bajo mínimo, no se duplica la tabla), vía `Producto::withSum('movimientos', 'cantidad')` + filtro en memoria, con link a `productos.index?bajo_minimo=1`. `ProductoController::index()` ahora soporta ese filtro (`request()->boolean('bajo_minimo')`) combinable con `?buscar=` (se preserva con un `<input type="hidden">` al buscar): agrega `withSum('movimientos', 'cantidad')` a la query solo cuando el filtro está activo y filtra en memoria sobre esa suma ya traída — corregido en review porque la versión original llamaba `Producto::bajoMinimo()` dentro del `filter()`, que reintroducía una query por producto del catálogo completo (el callback se evalúa antes de filtrar, no solo sobre el resultado chico esperado). (5) **Tendencia por tramo del mes** (`tendenciaPorTramoDelMes()`): hipótesis validada con el usuario de que el poder adquisitivo varía DENTRO del mes según el ciclo de cobro de sueldo (fin de mes/quincena, común en Argentina y Paraguay) — el corte es por **RANGO DE DÍA DEL MES** (1–10, 11–20, 21–fin de mes vía `DAY(created_at)`, con `BETWEEN 21 AND 31` para el último tramo porque `DAY()` nunca excede el último día real del mes), **no por semana ISO**, porque una semana calendario no coincide con el ciclo de pago. Histórico completo (todas las ventas de siempre, no solo el mes actual) — mejora con más meses acumulados, con poco volumen el ranking por tramo puede salir ruidoso (nota discreta en la vista). Total + % fiado (por MONTO, no por cantidad de ventas) de los 3 tramos en una sola query con `CASE WHEN` agregado en SQL; top 5 productos por tramo vía `topProductosPorCantidad()` (helper compartido, un query por tramo, mismo patrón join+groupBy+limit que (2)), productos ganadores resueltos con un solo `whereIn`. - **Offline: Ventas y Cobrar fiado (documento de alcance, sección 04)**. "Solo Ventas y Cobrar fiado funcionan offline — Service Worker + IndexedDB + UUID de dispositivo, sincroniza sola al volver la señal, sin duplicados." Es la pieza más compleja del sistema hasta ahora — detalle completo abajo porque una sesión futura va a necesitar entenderla para tocarla.

  - **Por qué es seguro (la premisa de la que depende todo lo demás)**: stock y saldo NUNCA se editan, se CALCULAN de un historial de movimientos (`MovimientoStock`, ventas/pagos) — ver el resto de este documento. Cada venta u pago offline es un INSERT nuevo, nunca una edición de algo existente, así que no hay conflicto de "edición simultánea" que resolver al sincronizar — el único problema real a resolver es la IDEMPOTENCIA (que un reintento de red no duplique la fila), no la concurrencia de escrituras.

  - **Idempotencia — `uuid_dispositivo`**: columna nueva (string, nullable, **UNIQUE**) en `ventas` y `pagos` (`database/migrations/tenant/2026_09_08_150000_*` y `_150100_*`). Se genera SIEMPRE en el frontend con `crypto.randomUUID()` — tanto si la venta/pago se manda online al toque como si se encola offline, un solo código server-side maneja los dos casos. `VentaController::store()` y `ClienteController::registrarPago()`: si ya existe una fila con ese `uuid_dispositivo`, responden como éxito SIN crear nada — un reintento de sync (red flaky, doble intento) no es un error, es un no-op. Dos capas, mismo patrón que el `lockForUpdate()` de stock (ver más abajo en este documento):
    1. Un `where(...)->exists()` ANTES de intentar crear — cubre el caso normal (reintento secuencial, ej. el ack de la primera respuesta se perdió).
    2. Un `catch (QueryException $e)` alrededor de la creación que detecta la violación de la constraint UNIQUE (`str_contains($e->getMessage(), 'uuid_dispositivo')`) y responde igual como éxito — cubre la carrera real de dos intentos casi simultáneos (ej. dos tabs, o un doble-tap de red) chocando contra la base.
    - `VentaRequest::withValidator()` salta ENTERO su pre-check de stock cuando viene `uuid_dispositivo` — sin esto, una venta offline con stock insuficiente (ver el punto siguiente) quedaría bloqueada ahí ANTES de llegar al controller, donde se decide de verdad qué hacer.

  - **Relajación de stock SOLO para ventas offline — decisión de negocio explícita, no relitigar**: una venta ONLINE sigue bloqueándose si deja stock negativo (`VentaController::store`, sin tocar — el pre-check de `VentaRequest` + el `lockForUpdate()` real dentro de la transacción, ver el bloque de Ventas más arriba en este documento). Pero una venta que llega por la cola OFFLINE no pudo validar el stock contra el servidor en el momento real de la venta (el cliente ya se fue con el producto en mano) — **se registra IGUAL aunque deje stock negativo**, nunca se rechaza una venta que ya sincroniza desde la cola offline. Columna nueva `ventas.sincronizada_con_stock_insuficiente` (boolean, default false) la marca para que el dueño la revise después. Gateado por la misma presencia de `uuid_dispositivo` que la idempotencia — una venta sin uuid (online normal) no cambia en nada. Visible en `ventas/index.blade.php` (etiqueta "⚠ sincronizada con stock insuficiente" en la fila, dueño y empleado la ven los dos — información, no una acción restringida) y en Reportes (conteo + link a `ventas.index?stock_insuficiente=1`, mismo criterio que el bloque existente de "Stock bajo mínimo").

  - **Cola offline del cliente — `resources/js/offline.js`** (importado desde `resources/js/app.js`, `type="module"` vía Vite): dos object stores de IndexedDB (`ventas_pendientes`, `pagos_pendientes`), cada fila keyeada por su `uuid_dispositivo`. Expone `window.offlineSync` (no `export` consumible por los `<script>` inline clásicos de las vistas, que no son módulos) con tres funciones:
    - `enviarOEncolar(form, tipo)`: punto de entrada único para un formulario offline-aware. Genera (o reusa) el `uuid_dispositivo` del form, y: si `!navigator.onLine` encola directo sin ni intentar la red; si está online intenta un `fetch()` real (`credentials: 'same-origin'`, `Accept: application/json`, body = el mismo `<form>` serializado a pares `[nombre, valor]` — 100% clonable por IndexedDB, a diferencia de un `FormData` crudo cuyo soporte de structured clone es desparejo entre navegadores) — si el fetch TIRA (TypeError de red real) encola; si el fetch RESPONDE pero con error (4xx/5xx real, no de conectividad) NO encola — devuelve el error tal cual, reintentar lo mismo no lo arregla solo.
    - `sincronizarPendientes()`: recorre la cola y reintenta cada item contra su `action` guardado. Se dispara sola en dos momentos — el evento `online` del browser, y una vez al cargar cualquier página si ya hay señal — sin que el cajero tenga que hacer nada. Si un item falla por RED, corta el recorrido entero (la red se cayó de nuevo a mitad de sync, reintentar el resto ahora no tiene sentido); si un item responde con error de servidor, sigue con el resto.
    - `contarPendientes()`: total ventas+pagos sin sincronizar, usado por el indicador del nav.
    - **A propósito SIN Background Sync API** del Service Worker (soporte de navegador desparejo, complejidad extra): un listener de `online` a nivel de página alcanza para el caso real de este negocio — un dispositivo que se usa activamente en el mostrador, no una PWA cerrada en segundo plano.

  - **`public/sw.js` dejó de ser no-op**: ahora cachea network-first el HTML de `/ventas/create` y `/clientes/{id}` (las dos únicas pantallas con una acción offline real) más los assets de Vite bajo `/build/` — sin esto, offline.js nunca llegaría a ejecutar: el navegador ni siquiera podría ABRIR la página estando offline. Sigue sin tocar Productos/Reportes/Usuarios a propósito (fuera del alcance offline). Nunca intercepta un POST (las ventas/pagos van directo a la red o a la cola de IndexedDB, jamás al Cache Storage).

  - **Los dos formularios offline-aware**: `ventas/create.blade.php` (submit del carrito, ya era JS puro) y `clientes/show.blade.php` (form de "Registrar pago", con `<x-confirm-dialog>`) llaman `window.offlineSync.enviarOEncolar()` en el punto donde antes hacían un submit nativo. UX distinta a propósito entre los dos, ver el porqué:
    - **Ventas**: éxito y encolado los dos resetean el carrito y se quedan en `/ventas/create` (nunca navegan) — es el flujo real de un mostrador, una venta atrás de la otra, forzar una vuelta a `ventas.index` por cada venta sería fricción pura.
    - **Pagos**: éxito recarga la página (`location.reload()`, con un `setTimeout` de 700ms para que se alcance a ver el mensaje) para reflejar el saldo/historial ya actualizados — SÍ importa acá porque la pantalla los muestra en primer plano. Encolado NO recarga (el saldo real todavía no cambió del lado del servidor, recargar mostraría el estado viejo sin explicar por qué).
    - Ninguno de los dos reusa el flash de sesión (`<x-status-banner>`) para el resultado del fetch — un mensaje propio (`#venta-feedback`/`#pago-feedback`, mismos 3 colores que el resto de la app: verde éxito, amarillo advertencia/encolado, rojo error) porque el flash de sesión se consumiría en el GET que el fetch sigue internamente al redirect de éxito, no en la navegación real del browser.
    - **Decisión ambigua, revisar si no convence**: la letra del pedido decía "mostrá el mensaje de éxito normal" para el caso online y "reseteá el carrito" solo para el caso encolado — interpretado acá como el mismo reset en los dos casos (ver el porqué arriba). Si la intención real era distinguir más los dos casos, es el primer lugar a mirar.

  - **GOTCHA de orden de scripts, ya resuelto pero fácil de repetir**: `@vite(...)` en `layouts/app.blade.php` emite `<script type="module">`, que el browser DIFIERE hasta después de parsear todo el HTML — corre DESPUÉS de cualquier `<script>` clásico inline que ya esté en el body (como los de las vistas y de `nav.blade.php`), no antes. `window.offlineSync` (definido dentro de ese módulo) puede no existir todavía si algo lo usa de forma SÍNCRONA al tope de un script inline. No es un problema real para los submit handlers (se ejecutan recién al click, mucho después de que el módulo ya corrió) pero SÍ lo era para el contador del nav — por eso `nav.blade.php` espera al evento `window.load` antes de llamar `contarPendientes()` por primera vez, en vez de hacerlo al tope del `<script>`.

  - **Tests**: cubierto lo que se puede probar server-side sin un browser real — `tests/Feature/VentaTest.php` (venta con uuid nuevo se crea normal; mismo uuid dos veces no duplica y responde éxito; uuid + stock insuficiente se crea marcada; SIN uuid + stock insuficiente sigue bloqueada — regresión) y `tests/Feature/PagoTest.php` (mismo patrón de idempotencia para Pago). Los tests de fecha (sección 1 y 2) congelan el reloj con `Carbon::setTestNow()` a mitad de una semana conocida (miércoles, mediodía) en vez de depender del día real en que corre la suite. Welcome: `GET /` responde 200 (cobertura mínima de la ruta pública, fuera de cualquier tenant).
